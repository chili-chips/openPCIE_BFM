# openPCIE_BFM: changes to pcieVHost and VProc

How openPCIE_BFM differs from upstream pcieVHost 1.9.3, VProc 1.13.4 and mem_model `c7b9c62` ([versions](vip/README.md)). Found on openPCIE, against the AMD `PCIE_2_1` hard macro under XSIM, and on openCologne-PCIE, under Verilator and Icarus. Issue numbers are those openPCIE used, so its notes still match.

## What we added

- **VProc: the user code as a coroutine, about 22 times faster, and deterministic.** Upstream runs each node's user code in a thread of its own, and hands over through two semaphores on every access: two system calls and a scheduler wake-up, millions of times per run. Ours runs it on the simulator's own thread, on its own stack; an access switches stacks in 21 instructions of x86-64 assembly, no kernel ([`vproc-coroutine.patch`](patches/vproc-coroutine.patch)). The results are identical, the HM run to the picosecond:

  | openCologne-PCIE EP model, Verilator, seed 1 | run 1 | run 2 | run 3 | run 4 | run 5 |
  |---|---|---|---|---|---|
  | threads, upstream | 17.7 s | 17.8 s | 17.2 s | 18.1 s | 17.9 s |
  | coroutines, ours | 0.8 s | 0.8 s | 0.8 s | 0.8 s | 0.8 s |

  Under XSIM the simulator's own kernel weighs more: openPCIE's `make RC=model` 32.5 s to 9.5 s (3.4 times), the HM run with its RTL CPU 65.9 s to 52.6 s.

  With one thread and no operating system scheduler in the handover, every run takes the same wall time. Threads had an intermittent slow mode (3 to 80 times slower, in 4 of 9 runs one evening, in none of 10 another), with the handover its prime suspect; 100 seeds under coroutines all took the same time. At 0.8 s a seed, 1000 seeds take about 13 minutes (under 2 with `REGRESS_JOBS=8`), where it took 5 hours before. Measured: 100 seeds of the EP model in openCologne-PCIE, 8 at a time, in 14 s, all PASS. On other CPUs, on Windows, and with `-DVPROC_THREADS` (for sanitizer runs: they do not follow stack switches), VProc keeps the threads, now retrying a wait a signal interrupts. A `VUserMain<n>()` that returns idles its node with an error message; upstream left the simulator waiting forever.
- **pcievhost: Data Link and Transaction access points, besides the PIPE.** Upstream, the link is visible only as PIPE symbols; TLPs and DLLPs stay inside the C model. Our transaction taps bring every TLP and DLLP sent and received out to ports, and `PIPExN__pcieVHost` offers them at the Data Link Layer (`dllp_*`, `dll_rx_*`) and the Transaction Layer (`tx_*`, `rx_*`) ([transaction taps](../2.rtl/README.md#transaction-taps)).
- **pcievhost: x4 PIPE.** Upstream's PIPE wrapper `pcieVHostPipex1` is x1 only. Ours, `pcieVHostPipexN`, runs the same model over any number of lanes; the self-test uses x1 and x4 (`make LANES=4`), and openPCIE x4 at Gen1 and Gen2 (`make SIM_LANES=4`, `SIM_GEN=2`); all pass ([the x4 link in WaveCrux](https://github.com/chili-chips/openPCIE/blob/main/5.sim/README.md#the-x4-link-in-wavecrux)).
- **pcievhost: Gen2 speed changes.** Upstream's LTSSM helper stops at L0 and has no Recovery.Speed. Ours follows the RC from L0 into Recovery and through a speed change, and can start one itself, Gen1 to Gen2 and Gen2 to Gen1 (in openPCIE: `make SIM_SPEED_TEST=1`, x1). All pass against the hard macro ([the Gen2 speed change](https://github.com/chili-chips/openPCIE/blob/main/5.sim/README.md#example-the-gen2-speed-change)).
